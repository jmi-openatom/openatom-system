# 招新压测脚本

运行环境：Python 3.9+，无第三方依赖。默认页面为 https://www.jmi-openatom.cn/apply/1，接口为 https://api.jmi-openatom.cn/api/v1/site/recruitment/1。

在项目根目录运行。建议从服务器外的电脑运行，避免与服务争抢 CPU，同时覆盖公网链路；确认本机代理/网络正常。本脚本直接连接目标，不读取 HTTP_PROXY / HTTPS_PROXY 等环境变量，不伪造 X-Forwarded-For。

## 只读测试（正式表单可用）

先逐级加压，每级 20 秒，分别模拟 10、30、50 个并发用户：

```sh
python3 scripts/recruitment_loadtest.py --stages 10,30,50 --duration 20
```

50 人持续 60 秒：

```sh
python3 scripts/recruitment_loadtest.py --users 50 --duration 60
```

100 人同时开始访问，每人请求一次 HTML、同源 JS/CSS 及一次表单详情 API：

```sh
python3 scripts/recruitment_loadtest.py --mode burst --users 100
```

单独测表单数据接口（默认每轮之后停留 1 秒）：

```sh
python3 scripts/recruitment_loadtest.py --mode api --users 50 --duration 60
```

`browse` 每轮按顺序读取页面 HTML 和详情 API，默认每个用户在每一级的第一轮下载一次同源 JS/CSS；`burst` 每人下载一轮；`api` 每轮只读详情。并发数指虚拟用户数，实际 RPS 由响应速度、资源数量与 `--think-time` 共同决定；不是 50 人每秒提交 50 次。持续模式到时停止发起新一轮，已开始的一轮资源/API 仍会完成，首次资源下载较大时实际运行可能明显超过 duration。Ctrl+C 停止发起新请求并保存报告，socket 超时默认为 10 秒。

## JS/CSS 下载策略

默认 `--assets once`：每个虚拟用户首次访问时下载一次资源，后续轮次跳过，近似该用户已有浏览器缓存。解析页面 script、stylesheet、modulepreload 与 script/style preload；递归解析静态 ESM import/export 和 CSS @import，按完整 URL 去重。针对本项目还提取 Vite 中 ApplicationForm、SiteLayout 的动态分块及 mapDeps 配套资源，不批量下载其他路由代码。资源只允许页面同源，第三方脚本、图片、字体和视频不下载。

每轮重新下载 JS/CSS，模拟持续有新用户进入的较重流量；不会添加随机参数绕过服务器缓存：

```sh
python3 scripts/recruitment_loadtest.py --users 50 --duration 60 --assets always
```

恢复旧版 HTML/API 测试，方便与以前的数据比较：

```sh
python3 scripts/recruitment_loadtest.py --users 50 --duration 60 --assets none
```

如果构建方式不同，或有未发现的动态分块，可以用重复的 `--asset-url /assets/实际文件名.js` / `--asset-url /assets/实际文件名.css` 补充，文件名以线上 HTML/浏览器 Network 为准，不要使用本地旧构建的哈希文件名。

HTTP 客户端顺序下载资源，不执行 JavaScript、不渲染页面；ESM/Vite 依赖提取为针对常见构建格式的静态解析，不能保证覆盖所有浏览器运行时请求。结果能反映这些 JS/CSS 的下载流量和成功率，仍不能直接当作完整首屏速度。请求支持 gzip/deflate，`bytes` 统计压缩后响应体，`decoded_bytes` 为解压后大小；不含 HTTP 头/TLS 开销，也不模拟 Brotli、HTTP/2、多资源并行下载、浏览器条件缓存请求。脚本不做登录或验证码测试。

## 报名提交测试（会真实写入数据库）

先建立独立测试招新批次，开放匿名报名；不要直接把正式批次 1 当成写入压测目标。提交模式使用真实出口 IP，可观察多人共用校园 Wi-Fi 时的限流情况。每个请求使用不同测试学号，POST 不自动重试。

复制 `scripts/recruitment-payload.example.json` 为自己的模板，修改 `campaignId`、`clubId`、志愿部门和表单自定义必填字段。示例里的 999 是占位批次，需换成实际测试批次。`profile.studentId` 必须同时保留 `{run_id}` 和 `{index}`；姓名保留“压测”标记便于辨认。字段与选项以测试批次表单为准。

```sh
python3 scripts/recruitment_loadtest.py \
  --mode submit --campaign-id 999 \
  --payload-file scripts/recruitment-payload.example.json \
  --allow-write --users 50 --count 50 --think-time 0
```

上例发起总共 50 次提交，最多 50 个并发用户，不是持续刷写。`--count` 决定总提交次数，`--duration` 不控制提交模式。脚本先检查批次、匿名报名设置及必填字段，不会自动创建/删除批次或申请。若同一真实 IP 的限流仍是每秒 5 次，出现 429 是限流策略的结果，不代表机器算力不足。

## 本地/测试环境

```sh
python3 scripts/recruitment_loadtest.py \
  --page-url http://127.0.0.1:5187/apply/1 \
  --api-base http://127.0.0.1:8921/api/v1 \
  --users 10 --duration 10
```

URL 需直达目标，不自动跟随重定向。HTTPS 校验证书，不提供跳过证书验证选项。

## 看报告

默认输出 `output/loadtest/运行编号/summary.json` 和 `requests.csv`；可用 `--output` 改目录。统计包括：

- HTTP 状态和业务 code（HTTP 200 但业务失败仍算失败）；页面必须返回 HTML，详情必须包含表单数据。
- 成功率、RPS、P50/P95/P99/最大响应时间、限流次数、缓存命中头。
- 每个 URL 单独统计，另有 `resource_kinds` 按 page/api/js/css 汇总，避免快速资源响应掩盖慢 API。
- CSV 新增 `resource_kind`、`content_encoding`、`decoded_bytes`；summary 包含总下载量、解压后大小及平均响应体 Mbps。平均 Mbps 不能代替服务器的瞬时出口带宽监控。
- 提交成功的申请 ID 保存在 CSV 的 `application_id` 列，用于核对测试数据。应在测试批次后台核对成功数与实际新增记录；脚本本身不查询数据库，也不证明没有额外重复记录。

延迟统计包含失败请求，查看成功率和错误分布后再判断容量。退出码：0=所有负载请求成功；1=存在失败；2=参数/预检失败；130=手动中断。预检只有一次只读详情请求，不计入统计。报告可能包含服务器错误消息，请先检查再对外分享。

针对明天的 50 人场景，建议验收：无意外 5xx/限流、表单 API P95 小于 1 秒、提交 P95 小于 3 秒且记录一致。这些是验收目标，不是已验证结果。服务器同时观察 CPU、可用内存、网络出口、MySQL 连接等待和 Redis 延迟；若测试机器 CPU/网络先满，结果也会受压测客户端限制。
