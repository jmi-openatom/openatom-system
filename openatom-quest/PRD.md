# OpenAtom Quest 新成员任务平台产品需求文档

> 产品名称：OpenAtom Quest（暂定）
> 文档版本：V1.0
> 产品阶段：MVP 需求定义
> 服务对象：开放原子开源社团新成员、导师、项目负责人及管理员
> 身份认证：仅支持 OpenAtom OAuth

## 1. 项目背景

新成员加入开放原子开源社团后，经常面临以下问题：

- 不清楚应该先学习什么、完成什么任务；
- 学习资料与任务分散在群聊、文档和代码托管平台；
- 完成任务后缺少统一的提交、审核和反馈渠道；
- 社团管理者难以准确掌握成员参与度和成长情况；
- 导师需要反复回答相同的入门问题；
- 优秀成员缺少清晰的晋升和真实项目参与通道。

因此，社团需要建设一个统一的新成员任务平台，把成员从加入社团、完成入门任务，到参与真实开源项目的全过程串联起来。

## 2. 产品定位

OpenAtom Quest 是一个面向开放原子开源社团的成员成长与任务实践平台，通过成长路线、任务提交、导师审核、积分徽章和项目实践，帮助新成员逐步成长为正式开源贡献者。

平台的核心不是单纯管理任务，而是回答成员在成长过程中的五个问题：

1. 我现在处于什么阶段？
2. 我接下来应该做什么？
3. 任务做到什么程度才算完成？
4. 谁会给我反馈？
5. 完成后可以进入哪个项目或承担什么角色？

## 3. 产品目标

### 3.1 核心目标

- 为新成员提供清晰、可执行的成长路线；
- 建立统一的任务领取、成果提交与审核反馈流程；
- 量化成员的学习过程与真实贡献；
- 帮助项目负责人发现并招募合适的贡献者；
- 降低导师和社团管理者的重复沟通成本。

### 3.2 MVP 成功指标

| 指标 | 目标值 |
| --- | ---: |
| OpenAtom OAuth 登录成功率 | ≥ 98% |
| 首次登录资料完善率 | ≥ 80% |
| 新成员首个任务领取率 | ≥ 70% |
| 新成员首个任务完成率 | ≥ 50% |
| 任务审核平均时长 | ≤ 48 小时 |
| 新人成长路线完成率 | ≥ 30% |
| 新成员进入真实项目比例 | ≥ 15% |

## 4. 用户角色

### 4.1 新成员

新成员可以：

- 通过 OpenAtom OAuth 登录平台；
- 完善个人资料并选择技术方向；
- 查看并完成新人引导；
- 查看成长路线和阶段进度；
- 领取、提交和重新提交任务；
- 查看导师审核结果与修改意见；
- 获取积分、等级和徽章；
- 浏览真实项目并申请加入。

### 4.2 导师

导师可以：

- 查看自己负责的成员和任务；
- 审核成员提交的成果；
- 退回任务并提供修改建议；
- 查看成员进度和历史提交；
- 标记优秀成果；
- 推荐成员加入真实项目。

### 4.3 项目负责人

项目负责人可以：

- 创建和维护自己负责的项目；
- 发布真实项目任务；
- 配置任务要求、所需技能和招募人数；
- 查看成员的项目申请和成长档案；
- 选择成员加入项目；
- 验收项目任务。

### 4.4 管理员

管理员可以：

- 管理本地成员状态和角色；
- 创建技术方向、成长路线和任务；
- 分配导师及调整任务负责人；
- 配置积分、等级和徽章规则；
- 查看全局运营数据；
- 处理审核申诉和异常积分；
- 查看重要操作日志。

## 5. 核心业务流程

```text
进入平台
  ↓
使用 OpenAtom OAuth 登录
  ↓
首次登录自动创建本地成员档案
  ↓
完善社团资料并完成新人测评
  ↓
选择技术方向
  ↓
系统生成或推荐成长路线
  ↓
领取并完成任务
  ↓
提交成果
  ↓
导师审核
  ├─ 退回修改 → 成员修改后重新提交
  └─ 审核通过 → 获得积分、经验和徽章
                         ↓
                    完成阶段认证
                         ↓
                    申请真实项目
                         ↓
                    成为项目贡献者
```

## 6. 身份认证与成员档案

### 6.1 登录方式

平台仅提供“使用 OpenAtom 账号登录”入口，不建设独立账号注册和密码体系。

- 用户点击登录按钮后跳转至 OpenAtom OAuth 授权页面；
- 授权成功后返回平台，由服务端完成身份校验并建立登录会话；
- 平台不提供手机号、邮箱、用户名密码或验证码登录；
- 平台不保存 OpenAtom 账号密码；
- 平台不提供找回密码和修改密码功能；
- OpenAtom 账号异常由 OpenAtom 统一账号体系处理。

### 6.2 首次登录

首次登录时，平台通过 OAuth 返回的稳定唯一标识自动创建本地成员档案，然后引导用户补充社团业务资料。

需要补充的资料包括：

- 姓名或社团昵称；
- 头像；
- 学校、学院、专业和年级；
- 感兴趣的技术方向；
- 已掌握的技能；
- GitHub 或 Gitee 主页；
- 每周可投入时间；
- 个人简介；
- 是否同意社团成员行为准则。

完善资料属于平台业务信息补充，不属于账号注册。

### 6.3 OAuth 账号关联规则

- 必须使用 OpenAtom OAuth 返回的稳定唯一用户标识关联本地成员；
- 不得仅通过邮箱判断用户是否相同；
- 同一个 OpenAtom 账号重复登录时不得创建重复成员；
- OAuth 仅负责身份认证，平台角色和业务权限由本平台管理；
- 首次登录用户默认获得“新成员”角色；
- 导师、项目负责人和管理员角色由管理员分配；
- 被平台禁用的成员即使 OAuth 认证成功，也不能进入业务页面。

建议保存的身份信息包括：

- OpenAtom 用户唯一标识；
- OAuth 提供方标识；
- 显示名称与头像；
- 授权范围内可获取的邮箱；
- 首次登录时间；
- 最近登录时间；
- 本地账号状态。

### 6.4 登录异常处理

| 场景 | 处理方式 |
| --- | --- |
| 用户拒绝授权 | 返回登录页并提示授权未完成 |
| OAuth 回调参数错误 | 提示登录失败并允许重新登录 |
| 授权码无效或过期 | 重新发起 OAuth 登录 |
| OpenAtom 服务暂时不可用 | 展示服务异常提示，不创建本地成员 |
| 本地成员已被禁用 | 阻止进入业务页面并提示联系管理员 |
| OAuth 返回信息不完整 | 登录后要求补充必要业务资料 |
| 重复回调 | 幂等处理，不重复创建用户或会话 |
| 登录会话过期 | 清理本地会话并重新进行 OAuth 认证 |

### 6.5 退出登录

- 清除平台本地登录会话；
- 清除或失效平台保存的访问令牌；
- 根据 OpenAtom OAuth 能力决定是否同步退出统一认证中心；
- 退出后返回统一登录页。

## 7. 新人引导

新成员首次登录并完善资料后进入新人引导：

1. 阅读社团介绍；
2. 阅读并同意成员行为准则；
3. 选择感兴趣的技术方向；
4. 填写技能自评；
5. 完成基础测评；
6. 查看系统推荐的成长路线；
7. 领取第一个新人任务。

平台应显示明确的引导进度，例如“新人引导已完成 4/7”。未完成引导的成员每次进入工作台时应看到继续完成入口。

## 8. 成长路线

### 8.1 成长阶段

| 阶段 | 名称 | 阶段目标 | 示例任务 |
| --- | --- | --- | --- |
| L0 | 新人报到 | 了解社团和基础规则 | 完善资料、阅读社团手册 |
| L1 | 开源入门 | 掌握开源协作基础 | Git、代码托管平台、提交 Issue |
| L2 | 技术学习 | 掌握所选方向的基础技能 | 前端、后端、AI、OpenHarmony 方向任务 |
| L3 | 项目实战 | 完成接近真实项目的实践任务 | 修复 Bug、实现小功能、完善文档 |
| L4 | 项目贡献 | 参与真实开源项目 | 提交 PR、参与评审、维护模块 |

### 8.2 技术方向

平台应支持管理员动态配置技术方向，初始可包括：

- OpenHarmony / ArkTS；
- 前端开发；
- Java 后端；
- Python 与人工智能；
- UI/UX 设计；
- 产品与社区运营；
- 技术文档；
- 测试与质量保障。

### 8.3 路线规则

- 一条成长路线由多个有序阶段组成；
- 一个阶段可以包含必做任务和选做任务；
- 任务可以配置前置任务；
- 成员完成阶段要求后进入下一阶段；
- 管理员可以为成员调整或补充任务；
- 已产生提交记录的路线和任务不可直接物理删除，只允许归档。

## 9. 首页工作台

首页应优先告诉用户“下一步应该做什么”。

### 9.1 新成员工作台

- 当前等级、积分和徽章；
- 当前成长路线与总体进度；
- 正在进行的任务；
- 待修改任务；
- 推荐的下一个任务；
- 最近收到的审核反馈；
- 即将截止的任务；
- 公告和近期活动。

### 9.2 导师工作台

- 待审核任务数量；
- 即将超过审核时限的任务；
- 负责的新成员；
- 进度异常成员提醒；
- 最近审核记录。

### 9.3 管理员工作台

- 新增成员与活跃成员数量；
- 任务领取和完成情况；
- 待审核数量；
- 各技术方向人数；
- 成长阶段分布；
- 新成员到真实贡献者的转化漏斗。

## 10. 任务中心

### 10.1 任务类型

- 新人必做任务；
- 技术学习任务；
- 实践挑战任务；
- 团队协作任务；
- 真实项目任务；
- 限时活动任务。

### 10.2 任务难度

- 入门；
- 初级；
- 中级；
- 高级。

### 10.3 任务状态

- 未开始；
- 进行中；
- 待审核；
- 需修改；
- 已通过；
- 已逾期；
- 已放弃。

### 10.4 任务字段

每个任务至少包含：

- 任务名称和简介；
- 所属技术方向与成长阶段；
- 任务类型和难度；
- 学习目标；
- 前置任务；
- 预计完成时间和截止规则；
- 操作步骤；
- 参考资料；
- 提交要求；
- 验收标准；
- 可获得积分和徽章；
- 负责人；
- 常见问题；
- 提交次数限制；
- 发布状态。

### 10.5 任务规则

- 支持成员主动领取和管理员直接分配；
- 支持个人任务和团队任务；
- 支持固定截止时间或领取后的倒计时；
- 支持限制领取人数；
- 未完成前置任务时不能领取后续任务；
- 任务支持草稿、发布、下架和归档；
- 成员领取任务后才能提交成果。

## 11. 成果提交

成员可以提交：

- 完成情况说明；
- 图片或截图；
- 文件附件；
- GitHub 或 Gitee 仓库地址；
- Pull Request 地址；
- 在线演示地址；
- 视频演示地址；
- 遇到的问题与学习总结；
- 是否使用 AI 工具以及 AI 参与的具体内容。

每次重新提交必须生成新的版本，不能覆盖历史提交。导师可以查看完整的提交和修改记录。

## 12. 审核与反馈

### 12.1 审核结果

- 审核通过；
- 退回修改；
- 判定不通过；
- 转交其他导师；
- 标记为优秀成果。

### 12.2 审核内容

- 审核结论；
- 文字评语；
- 分项评分；
- 必须修改项；
- 建议优化项；
- 做得好的部分；
- 是否允许再次提交；
- 示例或附件。

### 12.3 建议评分维度

| 维度 | 权重 |
| --- | ---: |
| 任务完成度 | 40% |
| 规范性 | 20% |
| 技术质量 | 20% |
| 学习总结 | 10% |
| 独立思考与创新 | 10% |

退回任务时必须填写原因和可执行的修改意见。成员对审核结果有异议时，可以发起申诉，由其他导师或管理员复核。

## 13. 积分、等级与徽章

### 13.1 积分来源

- 完成新人引导；
- 按时完成任务；
- 完成高难度任务；
- 提交优秀成果；
- 帮助其他成员；
- 参与社团活动；
- 提交有效 Issue 或 PR；
- 承担导师与审核工作。

积分应主要反映学习成果和真实贡献，不应依靠签到、登录或浏览行为大量发放。

### 13.2 等级示例

| 等级 | 名称 | 基本条件 |
| --- | --- | --- |
| L0 | 新人 | 首次登录并创建成员档案 |
| L1 | 开源学习者 | 完成新人路线 |
| L2 | 实践成员 | 完成技术基础路线 |
| L3 | 项目贡献者 | 完成至少一个真实项目任务 |
| L4 | 核心贡献者 | 持续贡献并通过管理员认证 |
| L5 | 导师 | 具备指导和审核资格 |

### 13.3 徽章示例

- 第一次提交；
- Git 入门；
- Issue 探索者；
- PR 贡献者；
- OpenHarmony 开发者；
- 文档贡献者；
- Bug 猎人；
- 优秀新人；
- 社区导师。

每个徽章包含名称、图标、获得条件、获得时间、关联任务或项目以及是否公开展示。

### 13.4 积分管理规则

- 每一次积分变动必须保存来源和时间；
- 同一业务事件不得重复发放积分；
- 管理员调整积分时必须填写原因；
- 异常积分可以撤销，但必须保留原记录和操作日志。

## 14. 成员成长档案

平台为每位成员生成成长档案，包括：

- 基础资料；
- 技术方向；
- 当前等级和总积分；
- 已获得徽章；
- 已完成任务；
- 优秀成果；
- 审核评分；
- GitHub 或 Gitee 贡献链接；
- 参与过的项目；
- 导师评价；
- 技能能力展示。

成员可以在申请真实项目时授权项目负责人查看成长档案。导师内部评价等敏感信息默认不公开。

## 15. 项目广场

### 15.1 项目信息

- 项目名称和简介；
- 项目仓库；
- 技术栈；
- 招募角色；
- 所需技能；
- 时间要求；
- 项目负责人；
- 当前成员；
- 可领取任务；
- 加入条件和招募状态。

### 15.2 项目申请

成员可以浏览项目、查看加入条件并提交申请。申请内容包括：

- 申请角色；
- 申请理由；
- 每周可投入时间；
- 相关技能；
- 已完成的代表任务；
- 授权展示的成长档案。

项目负责人可以通过、拒绝申请或要求补充信息，但只能查看项目招募所需的信息。

## 16. 消息通知

MVP 首先实现站内通知，通知场景包括：

- 任务审核通过；
- 任务被退回；
- 收到导师反馈；
- 任务即将截止；
- 新任务发布；
- 项目申请结果；
- 获得徽章或等级提升；
- 系统公告。

后续可以接入邮件、企业微信、飞书、钉钉或微信公众号。

## 17. 排行榜

排行榜作为辅助激励机制，不能作为评价成员的唯一依据。

可提供：

- 本周贡献榜；
- 本月成长榜；
- 优秀新人榜；
- 开源贡献榜；
- 助人榜；
- 各技术方向榜。

成员可以选择隐藏自己的排名。平台不突出展示低排名，并需要限制刷分行为。

## 23. 非功能需求

### 23.1 性能

- 普通页面首屏加载时间不超过 3 秒；
- 常规列表接口平均响应时间不超过 1 秒；
- MVP 应支持至少 1,000 名成员使用；
- 大文件使用对象存储，不直接保存在应用服务器。

### 23.2 安全

- OAuth 使用授权码模式；
- OpenAtom 支持 OpenID Connect 时优先使用 OIDC；
- OAuth 回调必须校验 `state`；
- 支持 PKCE 时应启用 PKCE；
- 客户端密钥只能保存在服务端；
- OAuth 回调地址必须使用 HTTPS；
- 访问令牌和刷新令牌必须安全存储；
- 禁止在前端代码、URL或普通日志中暴露令牌；
- 不记录完整授权码、访问令牌和刷新令牌；
- 所有业务接口必须在服务端校验权限和数据范围；
- 文件上传需要限制类型、大小并进行安全检查；
- OAuth 绑定、角色调整、账号禁用、审核和积分变更必须记录日志；
- 数据库应定期备份。

### 23.3 易用性

- 移动端可以正常浏览和提交任务；
- 任务状态使用统一颜色和文案；
- 页面明确展示下一步操作；
- 关键操作提供二次确认；
- 退回任务时必须填写原因；
- 表单应保留未提交的草稿，避免意外丢失。

### 23.4 可维护性

- 技术方向、成长路线、积分和等级规则应可配置；
- 任务、提交、审核和积分变动保留完整历史；
- 外部 OAuth 服务异常不能破坏已有业务数据；
- 外部通知或代码托管平台接入失败时，不应阻塞核心任务流程。

## 24. 核心业务规则

1. 用户只能通过 OpenAtom OAuth 完成身份认证；
2. 首次 OAuth 登录成功后自动创建本地成员档案；
3. OAuth 登录成功不等于自动获得管理权限；
4. 成员领取任务后才能提交成果；
5. 未完成前置任务时不能领取后续任务；
6. 每次重新提交都生成新版本，不覆盖历史记录；
7. 退回任务必须提供明确原因；
8. 每次积分变动必须保留来源记录；
9. 真实项目任务通过后才计入正式贡献；
10. 成员使用 AI 工具时必须说明使用范围；
11. AI 生成内容不能直接认定为成员个人能力；
12. 成员可以申诉审核结果；
13. 已产生业务记录的任务和路线不得物理删除，只允许归档；
14. 被禁用的成员不能进入业务系统，但其历史贡献记录应保留。

## 25. MVP 验收标准

### 25.1 身份认证验收

1. 未登录用户访问业务页面时进入 OpenAtom 统一登录页；
2. 平台不存在独立注册、账号密码、验证码和找回密码入口；
3. OAuth 授权成功后可以正确创建或匹配本地成员；
4. 同一个 OpenAtom 账号重复登录不会产生重复成员；
5. OAuth 认证失败时不会创建本地成员；
6. 新用户首次登录后进入资料完善和新人引导流程；
7. 已完成引导的用户登录后进入工作台；
8. 被禁用成员即使 OAuth 认证成功也无法进入业务页面；
9. 普通成员不能通过修改请求参数获得管理权限；
10. 退出登录后原平台会话立即失效。

### 25.2 核心业务验收

1. 管理员可以创建成长路线并发布任务；
2. 新成员可以选择技术方向并查看对应成长路线；
3. 新成员可以领取任务并提交成果；
4. 导师可以退回任务并填写修改意见；
5. 新成员可以依据反馈重新提交；
6. 导师审核通过后，系统自动发放积分并更新进度；
7. 成员可以收到对应的站内通知；
8. 管理员可以查看任务完成率和审核数据；
9. 不同角色的数据访问符合权限和数据范围要求；
10. 提交、审核、积分和关键管理操作均有历史记录。

## 26. 风险与待确认事项

项目进入技术设计前，需要进一步确认：

- OpenAtom OAuth 的授权地址、令牌地址和用户信息接口；
- OAuth 使用标准 OAuth 2.0 还是同时支持 OpenID Connect；
- 可申请的授权范围及能够返回的用户字段；
- OpenAtom 用户唯一标识字段及其稳定性；
- Token 有效期、刷新机制和撤销机制；
- 是否能够获取组织、社团或用户组信息；
- 正式环境允许配置的回调地址；
- OpenAtom OAuth 服务不可用时的官方处理规范；
- 成员、导师和管理员角色的实际审批流程；
- MVP 是否同时上线项目广场和徽章系统。

## 27. 产品原则

- 以成员成长为核心，不以功能数量为目标；
- 任务必须有明确目标、提交要求和验收标准；
- 反馈应具体、及时并能够指导成员修改；
- 积分和排名只能辅助激励，不能替代真实贡献评价；
- 身份认证统一依赖 OpenAtom OAuth，业务权限由平台独立控制；
- 所有自动化能力都不能破坏提交、审核和积分的可追溯性；
- 最终价值以新成员进入真实项目并持续贡献的比例衡量。
